STRATA Architecture

How the STRATA landing page is built, using the DOM model from class: page → body → sections → sub-sections → elements, where every element has a type, attributes and a value. Sections 01–04 describe the structure. Sections 05–10 follow the data: how a visitor moves, and the path an application takes from the button to an encrypted line on disk.

Browsersite/: HTML says what is on the page, CSS how it looks, JS how it behaves.
Serverserver.js: serves the files and receives applications. Built-in Node modules only.
Diskvault.js: encrypts and stores applications. The key is kept apart from the data.

01Page layout: from the board to our page

The same model as the whiteboard. The page is the body. The body is cut into horizontal sections. Each section is cut into sub-sections, those into smaller groups, and the smallest pieces are elements. Here the apply section is opened up three levels.

02The DOM tree

The DOM (Document Object Model) is the tree the browser builds from index.html. Rectangles are containers, ovals are leaf elements. Dashed boxes are branches that are folded to keep the figure readable. The red path is the branch that matters most: the application form.

04How JavaScript changes the tree

app.js never rewrites the page. It finds one node with querySelector and changes one attribute or one value. Everything else stays as the HTML wrote it. It uses textContent and createElement, never innerHTML, so text from a visitor can never become markup.

05The whole system

Three zones and one boundary. Everything that crosses the dotted line between browser and server travels over HTTPS. The data/ and keys/ folders sit outside site/, so a browser can never request them.

06How a visitor moves

The page is one long strip of six sections with one goal: get the visitor to apply. That is why every main button leads to the same place, section 5.

07The path of an application

Thirteen steps from pressing the button to the confirmation screen. Each check can stop the application, and the right-hand side shows how. The order matters: cheap checks come first, so a junk request never reaches the DNS lookup or the disk.

08How an application is stored

One application is one JSON line in an append-only file. The name, email and company never appear in plain text: they are inside ct. Each line holds the hash of the line before it, so a line cannot be removed or altered without being noticed.

What the server does at start-up

  1. Cuts off an unfinished lineIf the server crashed mid-write, the tail with no line break is removed. A copy of it is kept in a .crash-… file, so nothing is deleted silently.
  2. Compares the log with the backupIf the main file is missing or shorter than an intact backup, it is restored from backup/.
  3. Checks the chain and builds the indexesLoads every UUID and fingerprint into memory so repeats and duplicates are found without decrypting. Any break in the chain is written to the log.

10Plan: what comes next

Everything works locally today. To accept real applications, these steps come next, in this order.

  1. Hosting with HTTPSA server or VPS with Node 20+, a domain, and a free Let's Encrypt certificate instead of the self-signed one.
  2. Move the key to an environment variableSIGNUP_KEY instead of a file, with a copy in a password manager rather than on this server.
  3. Back up to another machineRegularly move data/backup/ elsewhere: a copy on the same disk does not survive that disk failing.
  4. Confirmation emailOnly an email proves a mailbox exists. The DNS check proves only that the domain accepts mail.
  5. Privacy policy and deletionA Privacy page, a retention period and a way to delete data on request (GDPR), agreed with the client.
  6. Details from the clientExact session dates, venue and faculty. They are not on the site yet because the brief did not include them.
